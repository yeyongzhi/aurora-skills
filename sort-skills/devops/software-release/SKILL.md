# 软件构建与发布

完成构建打包、版本维护、主分支集成、版本标签、安装包发布与产品文档站部署，让代码、产物与更新日志对应同一次发布。遵循用户指定的平台、版本和发布范围。

## 识别项目

- 读取仓库指引、Git 状态、远端、版本文件、构建脚本和 CI 工作流，确定产物为 `dist`、安装程序还是两者都有。使用项目既有工具链和锁文件，不猜测打包命令。
- 获取远端分支和标签，从远端默认分支及仓库配置识别主分支（例如 main 或 master）；两者同时存在时不能仅凭名称选择。
- 查找 VitePress 配置、文档目录、已有站点部署及更新日志，沿用现有路径、语言、格式和日期约定。完整发布时，没有 VitePress 站点就补建，有则完善；必须提供更新日志页面及其项目内 Markdown 源文件。
- 检查根目录 `README.md` 及已有多语言版本，核实产品定位、版本展示、下载入口、技术栈和作者公开联系方式，按下述规范补齐并随发布维护。
- 以最近一次已发布版本到本次发布内容为范围，结合提交和实际差异提炼变更。保留已有改动，不收录无关文件、凭据或生成目录。
- 完整发布请求涵盖必要的提交、推送、主分支合并、标签和 GitHub Release；只要求本地构建、预览或草稿时遵守该限制。仅在版本、目标仓库或范围存在影响结果的歧义时询问。

## 版本与更新日志

1. 采用 SemVer：不兼容变更递增主版本，向后兼容的新功能递增次版本，向后兼容的问题修复递增修订版本。递增主版本后次版本和修订版本归零，递增次版本后修订版本归零。纯构建、文档或维护发布默认递增修订版本；0.x 兼容性策略沿用项目约定。用户指定版本时检查格式、递增关系及冲突。
2. 正式发布标签固定为 `vX.Y.Z`，例如 `v1.4.2`，不得使用 latest 代替。预发布仅在用户要求时按 SemVer 使用后缀，并明确它与正式标签格式不同。
3. 同步项目实际使用的版本源及派生元数据，如包清单、工作区包、桌面应用配置和锁文件。使用既有版本工具，不全局替换所有版本字符串，不升级无关依赖。
4. 每次发布必须在项目的 Markdown 更新日志中添加本版本的实际更新内容，并让 VitePress 更新日志页面展示该内容，版本与发布日期一致。已有日志沿用原文件；没有时创建，例如 `docs/changelog.md`。每次尽量不超过 **5 条**：合并同类变更，描述用户可感知的结果，省略琐碎提交；确有必要超过时说明原因。每条以对应 emoji 开头，严格保持以下映射。

| 标记 | 更新类型 |
| --- | --- |
| ✨️ | 新增功能 |
| 🐛 | 问题修复 |
| 📝 | 文档更新 |
| 🎨 | 样式优化 |
| ♻️ | 代码重构 |
| 🧪 | 性能优化 |
| ⚡️ | 测试更新 |
| 📦️ | 构建更新 |
| 🌐 | 持续集成 |
| 🔧 | 日常维护 |
| ⏪️ | 版本回退 |

Release 说明复用这些精简条目。日志按版本倒序保留历史，不能只有版本号、日期或外链而没有更新内容，也不能只写在 GitHub Release 中。已有根目录 `CHANGELOG.md` 等日志时，优先通过 VitePress Markdown 包含或构建时生成页面复用同一内容源，避免手工维护两份；不编造功能或修复。

## README 产品化规范

完整发布时必须规范项目根目录 `README.md`，使其成为用户了解软件、获取最新版本和进入文档的首页。保留项目语言、品牌风格及有用的既有内容，按下表组织清晰的章节；已有多语言 README 时同步本次发布涉及的版本和链接。

| 内容 | 要求 |
| --- | --- |
| 软件说明 | 展示软件名称、一句话定位、用途和适用人群；有真实截图或演示时可复用，不堆砌宣传口号或虚构能力。 |
| 当前版本 | 明确展示当前代码对应的版本号，与项目版本源一致；尚未发布的版本标注开发中或待发布，预发布版本标明状态。 |
| 最新版本 | 提供醒目的“下载最新版本”或“查看最新发布”链接。GitHub 正式版可使用仓库的 `releases/latest`；预发布另列对应标签入口，不把它冒充最新稳定版。没有公开 Release 时如实说明尚未发布，并提供可用的安装或体验入口。 |
| 功能清单 | 简明列出当前已实现的核心功能，突出用户能完成的操作；计划功能另行标明。 |
| 安装与使用 | 提供最短可执行的安装、启动或体验步骤，并链接到站点的完整安装说明与使用说明。 |
| 开发简介 | 简述项目组成、开发环境，以及实际可执行的依赖安装、本地启动、构建命令；沿用真实包管理器和脚本，详细架构说明链接到项目文档。 |
| 技术栈 | 简单列出主要语言、框架、桌面运行时、构建及存储技术及其用途，以实际依赖和实现为准，不罗列全部包或混入未使用技术。 |
| 更新日志 | 使用“查看更新日志”等可点击链接，指向仓库内真实存在的 Markdown 日志；可同时提供 VitePress 日志页链接，不在 README 手工复制整份历史。 |
| 联系作者 | 使用项目已有或作者明确公开的联系方式，如 GitHub 主页、Issues、Discussions 或公开邮箱；缺少直接联系方式时可用仓库已有反馈入口，不猜测邮箱、社交账号或公开私人资料。 |

- README 顶部优先展示产品说明、当前版本、最新版本入口和文档入口；开发简介与技术栈保持简短，便于普通用户阅读。
- 每次发布同步检查版本号、支持平台、功能清单、下载和文档入口。仓库内文档使用正确的相对路径，在线站点和发布页面使用实际 URL；下载链接须指向对应仓库和真实资产，不能留下示例地址或待填占位符。
- 当前代码版本与最新已公开版本可能不同，必须按实际状态分别表达。发布前准备 README，正式发布后验证最新版本入口、安装资产及日志链接；远端尚未发布时不得声称新版本已可下载。

## VitePress 产品文档站与 GitHub Pages

完整发布必须包含以下站点工作；用户明确仅要求本地构建、打包或草稿时，不自行扩展为远端部署。

### 站点与内容

- 已有 VitePress 站点则补齐内容和部署，不重复搭建。没有时在合适的文档目录新增 VitePress；保留现有文档和其他框架站点，不覆盖已有应用入口。目录冲突时使用独立目录，并明确文档站入口。
- 沿用项目包管理器、工作区与锁文件，安装执行时可用的稳定版 VitePress，配置开发、构建、预览脚本。非 Node 项目可为文档站单独建立包清单与锁文件；忽略依赖、缓存和构建输出，提交文档源码与配置。
- 页面至少包含软件介绍（用途、适用场景）、安装说明（前置条件、下载入口、安装及首次启动）、使用说明（核心操作与必要示例）、功能清单、更新日志。根据真实代码和可用产物编写，不把计划功能写成已实现，不虚构下载链接或支持平台。
- 导航或侧栏必须能直接访问上述内容，更新日志必须有独立页面。日志 Markdown 源文件保存在项目中并纳入版本控制，每次发布同步更新。

### 仅主分支自动部署

- 新增或完善 `.github/workflows/` 下的 Pages 部署工作流，使用 GitHub Actions 构建 VitePress 并部署到 GitHub Pages。先核实当前 [VitePress 部署指南](https://vitepress.dev/guide/deploy#github-pages) 与 [GitHub Actions 工作流语法](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)，按实际工具链选用受支持的 Action 和 Node 版本，不照搬旧版本号。
- **唯一触发事件为推送到已识别的主分支**：主分支为 `main` 时设置 `on.push.branches: [main]`，为 `master` 时设置 `[master]`。两者同时存在时只填实际主分支，不把二者都列为部署分支。不添加标签、PR、定时或 `workflow_dispatch` 触发；不设置可能漏掉发布更新的路径过滤。软件安装包自己的标签发布流水线不受此站点触发规则影响。
- 部署 job 同时校验事件是 `push` 且 `github.ref` 等于实际主分支完整引用，例如 `refs/heads/main`；构建和部署使用同一次主分支提交。权限限于构建读取代码和 Pages 部署所需的 `contents: read`、`pages: write`、`id-token: write`，部署使用 `github-pages` environment，并通过 concurrency 避免并行部署互相覆盖。
- 流程包含签出、配置包管理器与 Node、按锁文件安装、构建文档、配置 Pages、上传站点产物及部署；产物路径使用实际 VitePress 输出目录。仓库 Pages 的构建来源设为 GitHub Actions；缺少设置权限时交付完整配置并报告待处理设置，不能声称已上线。
- 按最终 Pages 地址配置 VitePress `base`：项目站点通常为 `/<repo>/`，用户/组织主页或自定义域名通常为 `/`；核对实际域名和仓库设置。已有 Pages 站点时复用或协调现有发布流程与路径，避免两个工作流争抢同一站点或覆盖既有内容。
- 发布前完成文档生产构建和本地预览，验证导航、安装链接、更新日志及资源路径。推送主分支后等待对应提交的 Actions 成功，再检查 Pages 在线地址和本次日志；工作流配置完成不等于部署成功。

### GitHub Release 文案配置

- 每次准备 GitHub Release 时，除站点更新日志外，还要生成或更新发布说明配置 `release.yml`，并在发布前填好本次实际版本的标题与正文。这里指供发布流程读取的文案配置，不代表要在目标仓库新增 GitHub Actions 工作流；先检查仓库现有发布工具约定的路径和格式，沿用它们。若没有约定，生成可直接复制到 GitHub Release 表单的文案，不擅自添加工作流或改变项目发布架构。
- **除非用户明确要求其他标题格式，Release 标题必须且只能是完整版本标签**，与本次 Git 标签逐字一致，例如 `v1.4.2` 或 `v0.1.0-beta.6`。正式版和预发布版都不得添加软件名、空格、emoji、“测试版”“预发布版”、更新摘要或其他前后缀；例如 `MarkFlow v0.1.0-beta.6` 不符合默认规则。测试状态通过 GitHub 的 Pre-release 标记和正文表达。
- 正文以 `发布日期：YYYY-MM-DD` 开始，按日期实际填写，接着列出最多 5 条面向用户的变更。每条复用上方带 emoji 的更新日志条目，内容与本次提交、版本和站点日志一致。
- **beta 版本必须设为 GitHub Pre-release，并在正文末尾单独加入以下 Markdown 引用提示**，不能因版本号已有 `beta` 或页面已有 Pre-release 徽标而省略：

  ```markdown
  > 测试版，请先备份重要文档；遇到问题请通过 Issues 反馈。
  ```

  其他预发布版本同样设置 Pre-release 并保留测试提示；项目主要语言不是中文时使用含义一致的译文。正式版不加入该提示，也不标记为 Pre-release。
- 发布前核对 `release.yml` 的标题是否仅含版本标签、发布日期、变更条目和预发布标记是否与标签、资产及更新日志一致，并检查 beta 正文末尾的测试提示。发布说明最终使用该配置中的文案；使用 CLI、API 或自动发布工作流时显式传入标题，避免工具自动拼入软件名或摘要。发布后复核 GitHub Release 页面实际显示的标题、正文末尾提示和 Pre-release 状态。

## 集成、构建与发布

1. 提交发布所需的代码、版本元数据和日志，集成到最新主分支。可快进时优先快进，有分叉时遵循仓库合并策略；解决冲突后重新检查，不丢弃任一方代码。受保护分支通过 PR 和必要检查完成合并，权限或审核阻止合并时报告剩余事项，不声称发布完成。
2. 对合并后的最终发布提交运行适当检查、生产构建、打包命令及 VitePress 文档构建，验证日志页面。确认 dist 或安装程序真实生成且非空，核对嵌入版本、平台和架构。安装程序进行可行的启动或安装验证，说明未验证的平台；源码压缩包不算安装程序。
3. 产物必须来自最终发布提交。使用 CI 时确保工作流指向该提交并等待结果。标签触发的流水线先通过可在本地或分支执行的检查，再创建标签，等待构建成功后发布。代码或版本变化后重新构建，不上传旧产物。
4. 推送主分支，在最终发布提交上创建带注释的 `vX.Y.Z` 标签并推送该标签。验证远端主分支包含该提交、远端标签指向该提交。同名标签已存在时检查目标与发布状态，不移动、删除或强制覆盖已发布标签；冲突时停止该版本发布并说明原因。
5. **有安装程序时必须发布 GitHub Release 并上传安装资产**，使用对应标签与 `release.yml` 中已核对的标题和正文；按项目约定提供签名、校验文件和必要平台产物。使用现有 GitHub 连接器、CLI 或工作流，避免重复创建。可先暂存为草稿，全部必需资产成功后正式发布并验证下载链接。只有 dist 时交付构建目录，完成版本和标签流程；是否上传 dist 归档沿用用户或项目约定。
6. 验证主分支、版本、远端标签、Release 资产、README 版本与下载入口及日志一致。README、VitePress 站点、日志 Markdown 和 Pages 工作流随发布代码集成，通过主分支推送自动部署；核对对应 Actions 运行及在线日志，不额外部署到其他服务。

## 中断与交付

- 检查或构建失败时先修复再发布。缺少签名凭据、GitHub 权限、必要平台环境或主分支审核时，完成可独立执行的工作，明确阻塞项。
- 部分发布成功时保留现场，记录提交、已推送标签、Release 状态和已上传资产。重试先查远端，只补齐缺失步骤；上传失败不得报告成功，不自动删除公开发布或回退主分支。
- 不使用强制推送、破坏性重置或删除用户文件绕过冲突；并发更新后重新集成并验证。不打印或写入令牌、证书及密钥。
- 最终报告版本和标签、主分支及提交、产物绝对路径、验证结果、Release 链接及资产、`release.yml` 路径、README 更新情况、日志 Markdown 位置、VitePress 目录、Pages 地址、部署工作流及运行结果与未完成事项。没有安装包时明确产物为 dist；远端发布或站点部署未完成时明确当前状态。
