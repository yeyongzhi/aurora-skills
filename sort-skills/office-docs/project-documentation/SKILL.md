# 项目文档

帮助用户把初步想法或现有代码库整理成清晰、可执行的项目文档。核心交付物有：

1. **项目说明书**：项目目标、用户、功能范围、业务规则、使用流程和操作方法。
2. **技术开发说明书**：项目架构、技术方案、模块职责、数据与接口、安全和部署运维。

按用户需要产出其中一份或两份。两份文档要互相对应，并清楚标记哪些内容已确认、来自现状、属于建议或仍待确认。

## 工作原则

- 先理解再提问：阅读用户已经提供的信息；若是现有项目，先只读查看相关说明、目录、代码、配置和部署文件。不要重复询问已有答案。
- 不把假设写成事实。分别标记“已确认”“根据现状归纳”“建议方案”“假设”“待确认”。
- 只询问会实质影响范围、用户体验、架构、数据、安全、成本或交付的问题；小项目不套用企业级清单。
- 每轮集中询问约 3–5 个相互关联的问题。说明决策影响，必要时给出选项和推荐；用户允许代为决定时，采用合理方案并记录理由，不再反复确认。
- 用户回答后，简要复述已确认的决定、更新未决事项，只针对剩余的重要分歧继续提问。不要因次要细节阻塞初稿。
- 使用用户的语言。优先写清楚角色、行为、结果、约束和具体操作，少用空泛口号。
- 除非用户同时要求开发，不要为写文档修改应用代码。

## 工作流程

### 1. 明确情境和交付范围

从上下文判断这是新项目、现有实现还是改造计划；需要哪类文档、给谁阅读、语言/格式/位置是什么。能合理推断时就直接采用，不要为了填表而提问。

新项目描述设计意图，不声称已有实现。现有项目以仓库证据描述实际情况；必要时引用文件路径、模块或接口作为依据，并把建议与现状分开。

### 2. 整理需求地图

先把已知信息归纳，并找出影响文档的缺口：

- 项目要解决的问题、目标用户、目标和成功标准。
- 使用平台、角色、权限与账号生命周期（如适用）。
- 核心用户旅程、首期范围、暂不做的内容和后续计划。
- 业务规则、关键数据、外部服务或系统集成。
- 相关的隐私与安全、可访问性、性能、可用性、规模、语言或审计要求。
- 技术约束与偏好：客户端类型、现有技术栈、架构、存储、认证、部署环境、团队能力和预算。
- 必要的配置、发布、监控、备份、支持与维护要求。

按项目裁剪，不要要求每个项目都回答每个主题。

### 3. 分轮澄清需求

先用一小段复述当前理解，再按影响优先级提出具体问题。优先确认：

1. 谁会使用、关键流程是什么、首期必须包含什么。
2. 会显著影响权限、安全、敏感数据、集成或合规的要求。
3. 平台、技术约束、架构和部署等会决定技术方案的内容。
4. 对设计有影响的质量和运维要求。
5. 可以留到实现阶段决定的细节。

问题应解释为什么要问，并在有帮助时提供少量选项。例如：

- “需要同时支持桌面和手机浏览器吗？这会影响页面布局和导航。”
- “账号是否需要自助改密、找回密码和管理员重置？若首期只由管理员建号，可以先把自助找回列为后续项。”
- “团队有既定技术栈吗？如果没有，我可以结合部署环境和团队经验推荐；你更看重快速交付、现有生态还是后续扩展？”

不要因示例就默认用 Vue、某种数据库或固定登录方案。避免泛泛的长问卷；避免把架构偏好与业务需求混为一谈。用户只回答部分问题时，保留已明确内容，仅追问剩余的关键部分。

### 桌面软件专项需求

当用户提出开发桌面端软件时，在通用澄清流程中加入以下内容；已给出答案的事项直接记录，不重复询问。以下为本 Skill 的桌面项目默认要求，用户明确指定其他方案时以用户要求为准。

#### 平台与安装

- 用户未说明平台时，确认是单平台还是跨平台，并明确 Windows、macOS、Linux 的目标范围。不要把“桌面端”直接等同于 Windows，也不要因选择跨平台框架就声称所有平台均可交付。
- 记录各平台的最低系统版本、CPU 架构及安装包形式；不影响初稿的细节可标为待确认。
- 默认提供安装版，并支持自定义安装位置。区分 Windows 安装器选择目录与 macOS 应用放置位置，按平台说明实际支持的行为。

#### 安装目录与本地数据

- 默认将配置、业务数据、日志和用户资源集中存放在安装目录，方便查找、备份与迁移。配置采用 JSON，业务数据根据结构和事务需求选择 JSON 或 SQLite；不要仅因示例就固定数据库或文件名。
- 在技术文档中给出具体目录树，并区分随安装包发布的只读资源与运行时可变文件。例如 Windows 可写安装目录：

```text
D:\Tools\MyApp\
├── MyApp.exe
├── config.json        # 配置
├── data.db            # SQLite；也可按需求使用 data.json
├── logs\
│   └── app.log
└── resources\         # 用户导入的资源
```

- 在承诺目录方案前核实各平台的写权限、应用签名和更新方式。Windows 的受保护安装目录可能不可写；macOS 的已签名 .app 包不应作为可变数据目录。不要用“始终以管理员运行”解决日常数据写入，也不要静默改用其他目录。
- 若安装目录集中存储与目标平台存在冲突，说明具体限制并聚焦确认替代方案，例如用户选择的可写数据根目录，或平台标准应用数据目录；记录各平台最终路径及其与安装位置的关系。跨平台不代表物理目录结构必须完全一致。
- 明确首次启动的目录创建与写权限检查、配置原子保存、数据版本迁移、备份恢复、日志轮转，以及卸载时数据保留规则。升级必须保留配置、业务数据与用户资源，不能将其当作安装文件覆盖或删除。

#### 检查更新与 GitHub Releases

- 桌面项目必须包含“检查更新”功能，默认通过 GitHub Releases 分发版本。项目说明书需描述检查入口、当前与最新版本、更新说明、无更新、网络失败及下载或安装结果；是否启动时自动检查、是否自动安装可另行确认，不能将“检查更新”默认扩大为静默更新。
- 技术文档明确仓库与发布渠道、版本比较规则、各系统与架构对应的发布产物，以及采用框架更新器还是引导下载完整安装包。未给出仓库地址时标为待确认，不编造地址。
- 按所选框架的当前官方文档核实更新清单、签名与校验要求。不能将 GitHub Release 页面或 API 返回值直接当作框架更新清单；预发布版本默认不进入稳定渠道。
- 说明下载失败、校验失败、应用退出与重启、安装权限、数据迁移失败时的处理和恢复方式。发布流水线应产出匹配平台的安装包及更新所需元数据；签名私钥和访问令牌不得写入客户端或文档示例。

将平台、安装、数据位置和更新决定记入决策表，并分别落实到项目说明书的用户行为、技术开发说明书的实现约束和验收项。至少验证：目标平台安装与启动、目录写入、升级后数据保留、无更新、离线检查及无效更新产物的处理。

### 4. 维护决策与未决事项

在澄清过程中维护精简记录：

| 事项 | 当前结论 | 状态 | 原因或后续 |
|---|---|---|---|
| 技术栈 | 示例：Vue 3 | 已确认 / 建议 / 假设 / 待确认 | 决策依据 |

对重要技术决策记录取舍，不把建议冒充为用户确认。准备写文档前，简要回顾需求范围和关键决定。若仍有会改变方案的重要歧义，再进行一轮聚焦提问；否则带着明确标注的假设和待确认项开始起草。

### 5. 编写项目说明书

根据项目挑选适用章节，不必机械填满模板。通常包括：

1. 项目简介、问题背景、目标用户、目标与成功标准。
2. 项目范围：本期包含、不包含、优先级和后续规划。
3. 用户角色、权限与账号流程（如适用）。
4. 功能清单，建议为需求分配稳定编号（如 FR-001），记录优先级、适用角色、行为说明和验收要点。
5. 关键操作流程、完成结果、必要的异常与替代流程。
6. 业务规则、输入校验、通知及数据保留规则（如适用）。
7. 使用说明：前置条件、页面或入口、操作步骤、预期结果及常见问题。
8. 面向用户的安全、隐私和无障碍行为（如相关）。
9. 假设、待确认项和后续功能。

写用户能观察到的行为。例如密码修改章节要描述入口、验证、成功或失败反馈，而不只写“包含用户设置模块”。没有证据时，不要宣称某页面或功能已经上线。

### 6. 编写技术开发说明书

按项目规模和成熟度选择章节，通常包括：

1. 技术目标、约束及其与需求编号的关系。
2. 技术栈清单，标明是现有、已确认还是建议，并说明重要选择的理由。
3. 系统上下文和整体架构；能帮助理解时使用简洁的 Mermaid 图。
4. 模块边界、职责和主要依赖。
5. 已知的数据实体、关系、所有权和生命周期。
6. API、事件和外部集成；仅写有依据的接口契约。
7. 认证、授权、校验、隐私与安全设计（如适用）。
8. 配置、本地开发、构建、部署、迁移和回滚（如适用）。
9. 错误处理、日志、监控、备份与恢复（如适用）。
10. 测试与质量策略、性能/扩展考虑、主要风险及未决技术方案。

描述现有实现时，说明观察到的架构并在适当处指向代码位置；把改进建议单列。新项目写“拟议方案”，不要伪装成已落地内容。不要为了显得完整而编造表结构、接口、云资源或配置值。

### 7. 保持两份文档一致

- 项目名、角色、功能名、范围、优先级和决定状态保持一致。
- 条件允许时，用功能编号把技术模块、接口或数据映射回需求。
- 每个重要用户功能都应有技术实现说明，或明确标为待设计。
- 每个重要技术组件都应服务于某项需求，或说明其运维目的。
- 交付前检查两份文档之间的冲突并统一表述。

### 8. 保存并复核

- 遵循项目已有文档目录与命名；用户指定路径时按指定路径写入。没有既有约定的新项目可采用 docs/project-guide.md 和 docs/technical-design.md。
- 先检查同名或相关文档。用户要更新既有文档时更新目标文件；不得静默覆盖无关内容。
- 交付前检查无依据的断言、相互矛盾的范围、缺失的关键流程、未标注的不确定项和不必要的模板内容。
- 最终回复简要列出生成或更新的文件，并指出尚未决策且会影响实施的事项。

## 完成检查

- 目标读者能找到自己需要的信息：用户知道如何完成任务，开发者知道如何实现或哪些内容尚未决定。
- 功能、角色、关键流程和首期边界清楚。
- 已实现事实有项目证据；方案与假设有明确标签。
- 用户作出的决定被准确记录，待确认项没有被写成承诺。
- 产品需求与技术设计彼此对应，文档详略适合项目规模。
